# Sprint 04.7 — Browser and Accessibility Evidence

## Purpose and Boundary

Task 4.7 adds a reproducible browser and automated accessibility layer over the committed Task 4.6
test foundation. It does not activate a form, backend, database, clinical workflow, payment, or
fulfilment path. Tests use no patient data, production credential, or live vendor account.

## Controlled Tooling Contract

| Tool                |                       Version | Role                                             |
| ------------------- | ----------------------------: | ------------------------------------------------ |
| Playwright Test     |                        1.62.1 | Owns the local Vite server and browser projects. |
| Chromium            | 151.0.7922.34 / revision 1234 | Extension-free managed browser.                  |
| axe-core Playwright |                        4.12.1 | Automated WCAG A/AA rules over active routes.    |

`playwright.config.ts` uses one worker, zero retries, a fixed `127.0.0.1:8085` server, South African
locale/timezone, reduced motion, and blocked service workers. The two projects are desktop Chromium
at 1440 x 900 and a Pixel 7 profile. Screenshots and traces are retained only on failure; video is
disabled. `test-results/` and `playwright-report/` are ignored.
New workstations install the managed browser explicitly with `bunx playwright install chromium`.

## Findings and Corrections

The initial 48-case run passed 29 and identified four repeated accessibility defects plus three test
assumption errors. Product corrections were deliberately limited to presentation:

- Inline email, emergency, regulator, and terms links now have a persistent underline, so meaning
  does not depend on colour or hover.
- The gated general-support button uses the existing `text-primary-foreground` token, restoring
  sufficient contrast on gold.
- No public wording, health claim, route availability, metadata, or transactional behaviour changed.

The tests were corrected to use the actual approved homepage H1, wait for client hydration before
the mobile menu interaction, and recognize the expected console message generated by a deliberate
main-document 404.
